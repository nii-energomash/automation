# NuGet

Набор из двух воркфлоу для пакета, публикуемого в NuGet-реестр: `ci.yml` —
сборка по `push`, `publish.yml` — публикация по релизу. Лежит в
[`ci-src/.github/workflows/nuget/`](../ci-src/.github/workflows/nuget) и
[`ci-src/.gitea/workflows/nuget/`](../ci-src/.gitea/workflows/nuget),
копируется в `.github/workflows/` и `.gitea/workflows/` потребителя — сегмент
`nuget/` выбрасывается.

Здесь только то, чего в самих файлах не видно.

## Релизная модель

Версия публикуемого пакета берётся из git-тега `vX.Y.Z` и передаётся сборке
через `-p:Version`. В проекте она не хранится вовсе: в `csproj` версии нет, и
держать её в актуальном состоянии не надо. Разбор тега — в
[`prepare-nuget-release`](actions.md#prepare-nuget-release).

Единственный триггер публикации — **публикация релиза**, а не push тега.
Голый тег не публикует ничего: релиз это преднамеренный акт с release notes,
а тег ставится и по другим поводам. Отсюда способы починки: повторный прогон
— кнопкой Re-run, добор невыпущенного тега — созданием релиза на нём.
Переиздать уже выпущенную версию нельзя ни тем, ни другим — реестр не даёт
перезаписать пакет той же версии.

`-p:Version` повторяется в шаге `Pack NuGet` при `--no-build` намеренно: от
него зависят метаданные пакета и имя готового `.nupkg`, а не только сборка.

Прогон CI в публикации не переиспользуется: она сама пересобирает и
перепроверяет то, что выпускает.

## Что пакуется

`dotnet pack` вызывается без цели, то есть пакуется решение целиком. Отсюда
требование к проекту: в решении не должно быть пакуемых проектов сверх самого
пакета. Тестовые проекты в него не попадают — `Microsoft.NET.Test.Sdk` сам
выставляет `IsPackable=false`, — а вот консольный проект-пример попадает, и в
`publish.yml` цикл публикации отправит в реестр всё, что оказалось в `nupkg/`.

Три способа выполнить требование, в порядке предпочтения:

1. держать примеры в отдельном решении, как сделано в `NiiEnergomash.Pgc`;
2. выставить `IsPackable=false` непакуемым проектам;
3. указать цель явно, как сделано в `Kdepa.CommonChartTools`:

   ```yaml
   run: dotnet pack src/<Project>/<Project>.csproj --configuration Release --no-build --output ./nupkg
   ```

Третий способ надёжнее двух первых, но путь приходится подставлять в четырёх
файлах копии и держать в согласии с раскладкой проекта.

## Реестры и токены

На GitHub публикация идёт встроенным `GITHUB_TOKEN` при
`permissions.packages: write`. PAT здесь не нужен: встроенный токен не
истекает, не требует ручного обновления и ограничен своим репозиторием.

Одного блока `permissions` мало. `GITHUB_TOKEN` публикует только пакеты,
связанные с репозиторием прогона, а связь — отдельная сущность: она заводится
в момент **создания** пакета по `RepositoryUrl` из `csproj` и новыми выпусками
не переустанавливается. Пакет, впервые выпущенный с неверным адресом,
связаться не смог и будет отвечать 403 до тех пор, пока доступ не выдадут
вручную: Package settings → Manage Actions access → репозиторий с ролью Write.
Снятый грант возвращает 403.

У Gitea так не выйдет: автоматический `GITEA_TOKEN` не имеет авторизации на
запись в реестр пакетов, документация Gitea прямо предписывает обходиться
персональным токеном. Он лежит в секрете `GT_PACKAGES_TOKEN`.

## Дельта Gitea

Между площадками расходятся четыре вещи, и все они в `publish.yml`:

- `REGISTRY_URL`: на GitHub собирается из `github.repository_owner`, у Gitea —
  из `vars.REGISTRY_HOST` и `vars.REGISTRY_OWNER`;
- токен публикации: `secrets.GITHUB_TOKEN` против `secrets.GT_PACKAGES_TOKEN`;
- имя шага публикации: `Publish to GitHub Packages` против
  `Publish package to Gitea Registry`;
- комментарий к этому шагу: про встроенный токен на GitHub, про PAT у Gitea.

`ci.yml` у площадок совпадает целиком, кроме шапки.

Адрес Gitea собирается из переменных репозитория, а не пишется литералом:
хост внутренний, а `automation` публичный. Заодно перенос на другой хост не
требует правки воркфлоу.

Релиз в Gitea создаётся **отдельно**: зеркало тянет с GitHub только рефы,
события релиза через него не приходят. То есть выпуск версии на обеих
площадках — два действия, а не одно.

## Кеш пакетов

У `setup-dotnet` встроенного кеша нет — в отличие от `setup-node` с его
`cache: npm`, — поэтому каталог пакетов кешируется отдельным шагом
`actions/cache`, а его расположение задаётся переменной `NUGET_PACKAGES`.

Ключ считается по всем `csproj` и `Directory.Packages.props`: правка любого из
них инвалидирует кеш целиком, частичное попадание даёт `restore-keys`. То есть
выигрыш стабилен там, где список зависимостей меняется редко.

На Gitea шаг работает при живом кеш-сервере: его поднимает сам `act_runner`,
хранилище — на диске хоста раннера (`cache.dir`, по умолчанию
`$HOME/.cache/actcache`), а не внутри job-контейнера. У раннера в докере шаг
упирается в недоступный адрес и требует `cache.host` и `cache.port` в
`config.yaml`. Признак работающего кеша — строка `Cache saved with key: …` в
хвосте лога прогона.

Кеш зависимостей — не подмена источника: реестр пакетов Gitea хранит только
то, что в него запушили, upstream-прокси к nuget.org у него нет.

## Версии .NET

`DOTNET_VERSION` — величина проектная, она определяется таргетами `csproj`.
В наборе стоит список из двух версий, потому что SDK 10 собирает `net9.0`, а
`dotnet test` поднимает сборку каждого таргета на своём рантайме — значит
девятый нужен отдельно. Проекту с одним таргетом хватит одной строки.

## Опциональные шаги

Ничего из перечисленного в референс не входит — это шаги конкретных проектов,
приведённые здесь, чтобы их не изобретали заново:

- **Примеры отдельным решением.** Ломающие изменения публичного API ловятся
  сборкой примеров, а не юнит-тестами:

  ```yaml
  - name: Build samples
    run: dotnet build samples/<Project>.Samples.slnx --configuration Release
  ```

- **Документация DocFX.** Сборка работает как проверка — битые ссылки и
  невалидный `toc.yml` роняют шаг, — а готовый сайт выкладывается артефактом
  прогона. Нужна там, где репозиторий приватный и GitHub Pages недоступен:

  ```yaml
  - name: Restore .NET tools
    run: dotnet tool restore

  - name: Build documentation
    run: dotnet docfx docs/docfx.json

  - name: Upload documentation artifact
    uses: actions/upload-artifact@v7
    with:
      name: docs
      path: docs/_site
      retention-days: 14
  ```

  У Gitea выкладка артефакта опускается, сборка остаётся проверкой.

- **Ручной запуск.** `workflow_dispatch` в `on:` рядом с `push` — кнопка
  перезапуска CI без коммита.

- **Заглушка теста.** Пока тестового проекта в решении нет, шаг `Test` можно
  заменить на `echo`; в референс такая заглушка не идёт.

## Известные отклонения от источников

Набор собран из двух живых репозиториев, поэтому сверка по
[conventions.md](conventions.md) даёт непустой дифф с каждым из них. Ожидаемое
против `NiiEnergomash.Pgc`:

- шапка;
- в `ci.yml` — отсутствие четырёх шагов в хвосте (`Build samples`,
  `Restore .NET tools`, `Build documentation`, `Upload documentation
  artifact`) и абзаца о DocFX в шапке;
- комментарии к шагам `Cache NuGet packages` и `Pack`, которых у источника
  нет;
- в `publish.yml` — обобщённый комментарий к шагу публикации на GitHub: у
  источника он описывает однажды выданный вручную грант и ссылается на его
  `CONTRIBUTING.md`;
- единая формулировка комментария к `DOTNET_VERSION` на обеих площадках.

Против `Kdepa.CommonChartTools` дифф крупнее: там нет кеша и реальных тестов,
`Pack` нацелен на конкретный `csproj`, а в `on:` есть `workflow_dispatch`.
Сверяться с ним построчно смысла нет — он второй источник, а не канонический.

Дифф с `NiiEnergomash.Pgc` сверх перечня означает, что разъехались либо копии,
либо референс.
