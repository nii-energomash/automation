# npm

Набор из двух воркфлоу для пакета, публикуемого в реестр npm: `ci.yml` —
сборка по `push`, `publish.yml` — публикация по релизу. Лежит в
[`ci-src/.github/workflows/npm/`](../ci-src/.github/workflows/npm) и
[`ci-src/.gitea/workflows/npm/`](../ci-src/.gitea/workflows/npm), копируется
в `.github/workflows/` и `.gitea/workflows/` потребителя — сегмент `npm/`
выбрасывается.

Здесь только то, чего в самих файлах не видно.

## Релизная модель

Версия публикуемого пакета берётся из git-тега `vX.Y.Z` и проставляется в
манифест на время прогона. В git манифест сохраняет свою референсную версию:
в реестр она не уезжает никогда, и держать её в актуальном состоянии не надо.

Единственный триггер публикации — **публикация релиза**, а не push тега.
Голый тег не публикует ничего: релиз это преднамеренный акт с release notes,
а тег ставится и по другим поводам. Отсюда способы починки: повторный прогон
— кнопкой Re-run, добор невыпущенного тега — созданием релиза на нём.
Переиздать уже выпущенную версию нельзя ни тем, ни другим — реестр не даёт
перезаписать `name@version`.

`fetch-depth: 0` в checkout нужен не для сборки, а для выбора dist-тега:
чтобы понять, старший ли это тег, нужен весь их список.

## dist-теги

Выбор dist-тега — `latest`, `next` или `lts-vN` — делает
[`prepare-npm-release`](actions.md#prepare-npm-release), там же описаны входы
и причина префикса `lts-`. Политика вынесена в экшен намеренно: она обязана
совпадать на обеих площадках, поэтому существует в одном экземпляре.

## Реестры и токены

Реестр и scope передаются в `setup-node` через `registry-url` и `scope`. Тот
пишет в `.npmrc` прогона scoped-строку вида `@scope:registry=…` и авторизацию
через `NODE_AUTH_TOKEN`. Коммитить `.npmrc` в репозиторий не нужно, и адрес
реестра не попадает в манифест.

На GitHub публикация идёт встроенным `GITHUB_TOKEN` при
`permissions.packages: write`. PAT здесь не нужен: встроенный токен не
истекает, не требует ручного обновления и ограничен своим репозиторием.

У Gitea так не выйдет: автоматический `GITEA_TOKEN` не имеет авторизации на
запись в реестр пакетов, документация Gitea прямо предписывает обходиться
персональным токеном. Он лежит в секрете `GT_PACKAGES_TOKEN`.

## Дельта Gitea

Между площадками расходятся четыре вещи, и все они в `publish.yml`:

- `REGISTRY_URL`: на GitHub литерал `https://npm.pkg.github.com`, у Gitea
  собирается из `vars.REGISTRY_HOST` и `vars.REGISTRY_OWNER`;
- токен публикации: `secrets.GITHUB_TOKEN` против `secrets.GT_PACKAGES_TOKEN`;
- имя шага публикации: `Publish to GitHub Packages` против
  `Publish to Gitea Registry`;
- комментарий к этому шагу: про встроенный токен на GitHub, про PAT у Gitea.

`ci.yml` у площадок совпадает целиком, кроме шапки.

Адрес Gitea собирается из переменных репозитория, а не пишется литералом:
хост внутренний, а `automation` публичный. Заодно перенос на другой хост не
требует правки воркфлоу.

Релиз в Gitea создаётся **отдельно**: зеркало тянет с GitHub только рефы,
события релиза через него не приходят. То есть выпуск версии на обеих
площадках — два действия, а не одно.

## Проверки уровня проекта

Формат, `publint` и прочие проверки, привязанные к конкретному проекту,
шагами воркфлоу не заводятся. Их место — `pre`- и `post`-скрипты манифеста:

```json
"prebuild": "prettier --check .",
"build": "tsc",
"postbuild": "npm run lint:publish"
```

`npm run build` тянет их сам, поэтому шаг `Build` покрывает и сборку, и
проверки. Отдельный шаг рядом с ним означал бы, что одна и та же команда
выполняется в прогоне дважды.

Выигрыш не только в этом: локальная сборка проверяет ровно то же, что CI, а
набор проверок меняется в манифесте — копию воркфлоу трогать не приходится,
и она не расходится с референсом на ровном месте.

## Опциональный шаг: сверка генерации

Репозиторию с генерируемым клиентом нужен шаг, которого к `build` не
подвесить, — он сверяет рабочую копию:

```yaml
- name: Generation check
  run: |
    npm run generate
    git add --intent-to-add .
    git diff --exit-code
```

Это сверка, а не генерация: спецификация берётся из репозитория, в сеть шаг
не ходит и ничего не коммитит. Падает, когда закоммиченный вывод разошёлся
со спецификацией или с версией генератора.

`git add --intent-to-add` нужен, чтобы в дифф попали новые файлы: без него
`git diff` их не видит, а смена версии генератора вполне может их добавить —
то есть ровно тот случай, ради которого шаг и заведён.

Ставится в `ci.yml` перед `Build`.

## Манифест не в корне

Если `package.json` лежит в подкаталоге, к базовому набору добавляются три
настройки, и все три обязательны — пропуск любой ломает прогон:

```yaml
# в job, рядом с runs-on
defaults:
  run:
    working-directory: package

# в setup-node
cache-dependency-path: package/package-lock.json

# во входах prepare-npm-release
manifest-dir: package
```

Последнее — не дублирование первого: `defaults.run.working-directory` уровня
job на шаги композитного действия не распространяется, каталог передаётся
экшену явно.

## Известные отклонения от источников

Набор собран из двух живых репозиториев, поэтому сверка по
[conventions.md](conventions.md) даёт непустой дифф с каждым из них. Ожидаемое:

- против `kdepa-api-sdk` — шапка, отсутствие шагов `Generation check` и
  `Format check`, имя шага без пометки `(манифест остаётся 0.0.0 в git)` и
  обобщённая фраза про версию манифеста;
- против `kdepa-api-client` — шапка, отсутствие трёх строк подкаталога и та
  же обобщённая фраза (у client она уточнена скриптами генерации пакета).

Всё остальное совпадает построчно. Дифф сверх этого перечня означает, что
разъехались либо копии, либо референс.
