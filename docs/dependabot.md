# Dependabot

Обновление пинов сторонних экшенов. Копируется один в один:

```
ci-src/.github/dependabot.yml  →  .github/dependabot.yml
```

Только на GitHub: в Gitea Dependabot отсутствует как явление.

## Что в референсе есть

Ровно один блок — `github-actions` с корневым `directory: '/'`, недельным
расписанием, префиксом коммита `ci` и группировкой по `*`, то есть все
обновления экшенов приезжают одним PR.

Этот блок одинаков во всех шести живых репозиториях, где он есть
(`Kdepa.Api`, `kdepa-math-api`, `kdepa-api-client`, `kdepa-api-sdk`,
`Kdepa.CommonChartTools`, `NiiEnergomash.Pgc`) — совпадает до символа.
Разошлись только комментарии над ним: четыре формулировки одной мысли.

## Чего в референсе нет и почему

Блоков `npm`, `nuget`, `pip`. Это зависимости самого проекта, а не его CI:
они зависят от того, где лежит манифест, чем порождается лок-файл и требует
ли реестр аутентификации. Общего варианта у них не бывает, поэтому они
дописываются на месте, а не приезжают отсюда.

Живые примеры, по которым видно, насколько они проектные:

- **`kdepa-api-client`** — `npm` с `directory: '/package'`: манифест лежит в
  подкаталоге.
- **`kdepa-api-sdk`** — `npm` с `directory: '/'` плюс `ignore` на
  `@hey-api/*` (генератор в `0.x`, минор ломает вывод) и на `typescript >=7`
  (иначе `typedoc` роняет `npm ci` всей группе).
- **`Kdepa.Api`** — блока нет, вместо него комментарий, почему `nuget` не
  подключён: часть пакетов лежит в GitHub Packages, реестру нужна
  аутентификация через `registries` с секретом из хранилища Dependabot, а не
  из секретов Actions.
- **`kdepa-math-api`** — блока нет, комментарий про `pip`: лок-файлы
  порождает `pip-compile`, причём `requirements-astra.txt` — на другом
  интерпретаторе и в другой среде, и Dependabot пересобрал бы их своим
  резолвером в своей.

Отсюда правило: **выключенная экосистема описывается комментарием, а не
отсутствием.** Пустое место читается как «забыли», комментарий — как
«решили».

## Gitea

Dependabot там не работает вовсе. Пины в `.gitea/workflows/` поднимаются
вручную вслед за принятым на GitHub обновлением — это и записано в
комментарии внутри самого файла, чтобы уезжало вместе с копией.

Порядок такой: сначала влить бамп на GitHub, затем перенести те же версии в
`.gitea/`, проверив, что тег доехал до зеркала. «Актуально на github.com» не
равно «есть на зеркале».

## Чего делать нельзя

Класть шаблон в настоящий корневой `.github/` этого репозитория. Там он не
«не сработает» и не «сработает лишний раз» — он **станет** конфигурацией
репозитория, потому что Dependabot читает единственный жёстко заданный путь
`.github/dependabot.yml`.

Это тот же капкан, что и с шаблонами воркфлоу, но строже: воркфлоу для
запуска нужен подходящий триггер, а `dependabot.yml` довольно имени и места.
Замок стоит в самопроверке — см. [selfcheck.md](selfcheck.md).

## Конфигурация самого репозитория

Своя, лежит в `.github/dependabot.yml` и шаблоном не является. В ней две
записи: корень и перечень каталогов под `ci-src/`, чтобы пины в шаблонах не
отставали.

Перечень явный, потому что рекурсии нет. По исходникам `dependabot-core`
(`github_actions/lib/dependabot/github_actions/file_fetcher.rb`, метод
`workflow_files`): при `directory: '/'` берутся корневые `action.yml` и
`action.yaml` плюс содержимое `.github/workflows`, а при любом другом
`directory` — все файлы по маске `*.yml` **ровно в указанном каталоге**.
Новый каталог типа поэтому требует новой строки в списке.

Каталогов экшенов в списке нет: в каждом `action.yml` ровно один шаг
`run: bash "$GITHUB_ACTION_PATH/run.sh"`, внешних `uses:` там нет и брать
нечего. Каталог добавляется тогда, когда в его экшене появится обращение к
чужому действию.

Разбор шаблонов Dependabot'ом расположения не касается: он смотрит верхний
уровень YAML — `jobs`, иначе `runs`, иначе ничего
(`workflow_file/uses_collector.rb`, метод `workflow_root`). То, что файлы
лежат вне `.github/workflows/`, ему безразлично.

## Базовые образы

Экосистема `docker` не заведена ни в своей конфигурации, ни в шаблоне, хотя
`Dockerfile` в репозитории теперь есть — под `deploy/docker/`.

Причина та же, по которой сюда не приезжают `npm`, `nuget` и `pip`, плюс своя:
поднимать пины базовых образов здесь некому. Собрать и проверить их нечем —
контекста проекта нет, — а бамп без проверки нарушает правило «содержимое
приезжает из живого репозитория». В проекте это решается на месте, как и
остальные экосистемы зависимостей.

Пин образа `rhysd/actionlint` в самопроверке Dependabot не видит по другой
причине: экосистема `docker` смотрит на `Dockerfile`, а не на `docker run`
внутри шага. Он двигается вручную — см. [selfcheck.md](selfcheck.md).
