# automation

Референс CI/CD-конфигураций для проектов организации. Отсюда **копируют**:
в целевом репозитории размещается копия воркфлоу, действия или конфига, а не
ссылка сюда.

## Как брать

Основной путь — копия. Файл кладётся в репозиторий проекта по пути, указанному
в его шапке, и дальше живёт своей жизнью: правки в проекте сюда сами не
возвращаются, а обновление здесь само не доезжает до копий.

Прямое подключение по `uses:` остаётся возможным для экшенов и только на
GitHub. Это побочная возможность, а не опора: воркфлоу отсюда не вызываются,
а Gitea ссылку на github.com не разрешает.

Куда какой файл кладётся — в [docs/copy-map.md](docs/copy-map.md); правила
оформления и порядок сверки с живым репозиторием — в
[docs/conventions.md](docs/conventions.md).

## Что здесь лежит

```
ci-src/                    слепок CI-части репозитория-потребителя
  .github/
    workflows/
      npm/                 ci.yml, publish.yml
      nuget/               ci.yml, publish.yml
      docker/              ci-python.yml, ci-dotnet.yml, publish-sha.yml,
                           release.yml, registry-cleanup.yml
    actions/               экшены только для GitHub
    dependabot.yml         пины экшенов, только для GitHub
  .gitea/
    workflows/
      npm/ nuget/ docker/  те же файлы с дельтой площадки
    actions/               экшены только для Gitea
  .ci/
    actions/               экшены, общие для обеих площадок
deploy/                    как сервис доводится до работы у потребителя
  systemd/
    dotnet/ python/        install.sh, *.service, *.env.example
  docker/
    dotnet/ python/        Dockerfile и .dockerignore сервиса
    spa/                   то, что уезжает внутрь образа
project/                   конфиги проекта, которые читает сборка
  npm/                     .npmrc и сторож при package-lock.json
runners/gitea/             образцы config.yaml, compose и .env раннера
docs/                      индекс и разделы по темам
.github/                   своё, не шаблоны: самопроверка, dependabot.yml
```

Наполнение приезжает по шагам, порядок работ —
в [#31](https://github.com/nii-energomash/automation/issues/31). Сейчас
заполнены `.ci/actions/`, площадочные `actions/`, наборы npm, nuget и docker
для обеих площадок, `dependabot.yml`, настройки раннера Gitea в
`runners/gitea/`, раздел `deploy/` — установка службой systemd, `Dockerfile`
профилей `dotnet` и `python` и конфиг, уезжающий внутрь образа, — и профиль
`npm` в `project/`. У профиля `spa` вместо `Dockerfile` лежит заготовка
`Dockerfile.draft`: она не копируется, почему — в
[docs/deploy.md](docs/deploy.md).

Шаблоны воркфлоу лежат под `ci-src/`, а не в корневом `.github/workflows/`,
намеренно: триггеры у них настоящие (`push`, `schedule`, `release`), и в
корне они запускались бы здесь — чистка реестра пошла бы по ночам, публикация
срабатывала бы на релизе этого репозитория.

С `dependabot.yml` то же, но строже: воркфлоу для запуска нужен подходящий
триггер, а конфигурации Dependabot довольно имени и места — `.github/`
в корне читается им как единственный источник настроек. Под `ci-src/`
поэтому уезжает не только то, что запустилось бы, но и то, что применилось
бы. Что в корневом `.github/` допустимо, проверяется самопроверкой:
[docs/selfcheck.md](docs/selfcheck.md).

## Архив прежнего подхода

Прежде отсюда подключали воркфлоу и действия по `uses:`. Подход прекращён,
его срез лежит в ветке [`v1`](../../tree/v1) и релизе
[`v1.0.0`](../../releases/tag/v1.0.0). Это архив: он не развивается и
потребителей туда не переводят.
